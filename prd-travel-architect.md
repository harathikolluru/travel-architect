**Status:** Draft v1

## 1. Problem Statement

Time-poor independent travelers planning a 3–7 day trip to an unfamiliar destination spend hours stitching together attractions, food, transit, and weather across a dozen tabs — and still end up with a plan they can't trust. Generic AI tools produce a plausible itinerary, but it breaks on the ground: closed restaurants, days that zigzag across the city, no rain plan, invented addresses. The cost of not solving it: the traveler wastes prep time *and* vacation days, and loses confidence that any plan will hold.

## 2. Goals

1. **Generate a complete, grounded trip plan in one pass** — from minimal input to itinerary + restaurants + packing list + map, with no manual research required.
2. **Make the plan demonstrably resilient** — every itinerary day is geographically clustered, weather-adapted, and carries a backup in every activity/meal slot.
3. **Ground every fact in real data** — 100% of surfaced places and weather come from live APIs, never model memory. Zero invented addresses or opening hours.
4. **Make the intelligence visible** — every itinerary item carries a one-line rationale explaining the geography/weather/interest logic.
5. **(Portfolio goal) Produce a single screen that proves the product is smarter than a chatbot list** — the map + reasoning view a reviewer can grasp in under 30 seconds.

## 3. Non-Goals

1. **No families/business/group modes.** Different constraint engines (nap schedules, meeting optimization, group consensus). Separate product — v2+.
2. **No post-trip recap video.** High effort, fragile, unrelated to the planning wedge. Replaced by a static shareable summary.
3. **No real-time on-trip re-planning.** v1 produces a plan *before* the trip; live recovery requires real-time infra and is out of scope.
4. **No actual bookings/reservations/payments.** We *recommend* open, bookable places; we don't transact. Avoids OTA-level complexity and liability.
5. **No multi-destination / multi-city trips.** One destination per plan keeps geographic clustering tractable.

## 4. User Stories

### Maya — Time-Poor Explorer (primary)
- As an independent traveler, I want to enter my trip details and get a complete day-by-day plan, so that I don't have to research across a dozen sites.
- As a traveler with dietary needs, I want restaurant recommendations filtered to my diet, so that every suggestion is one I can actually eat at.
- As someone who distrusts AI itineraries, I want to see *why* each item was chosen (weather, location, my interests), so that I trust the plan enough to follow it.
- As a traveler, I want each day's stops clustered geographically and shown on a map, so that I'm not crossing the city twice a day.
- As a traveler, I want a packing list based on the actual forecast, so that I pack for the weather I'll get.

### Dan & Priya — Weekend Couple (secondary)
- As a couple, we want to enter two sets of interests and get a blended plan, so that neither of us has to compromise every day.
- As a couple, we want a one-tap alternative for any slot, so that we can swap something we're not feeling without re-planning the day.

### Sam — Spontaneous Optimizer (secondary)
- As a last-minute traveler, I want a great plan even when I leave most fields blank, so that I get value from minimal input.
- As an anxious planner, I want sensible defaults I can refine, so that I'm not blocked by a long form.

### Edge / error states
- As a traveler, when a destination has thin data coverage, I want to be told clearly rather than shown invented places.
- As a traveler, when I enter invalid dates (past, or >7 days), I want a clear correction prompt.
- As a traveler, when no restaurant matches my diet + budget + location, I want an honest "closest options" fallback rather than a fabricated match.

## 5. Requirements

### Must-Have (P0) — feature is not viable without these

**P0.1 — Trip intake**
Capture destination, travel dates, budget, pace, interests, dietary preferences, must-visit places.
- [ ] Required: destination + dates. All other fields optional with sensible defaults.
- [ ] Dates validated: not in the past, duration 3–7 days (warn but allow outside range).
- [ ] Accepts multiple/blended interests (serves Dan & Priya).
- [ ] Blank optional fields produce a complete plan via defaults (serves Sam).

**P0.2 — Grounded place & weather data layer**
- [ ] Places (attractions + restaurants) come from a live API with name, location (lat/lng), category, and opening hours where available.
- [ ] Weather forecast retrieved per destination per travel date.
- [ ] No place or hour is ever generated by the LLM. Given missing data, the item is omitted or flagged — never fabricated.

**P0.3 — Day-by-day itinerary**
- [ ] One block per travel day, paced to the user's stated pace (relaxed/moderate/packed).
- [ ] Each day's stops are geographically clustered (proximity grouping).
- [ ] Each day adapts to that day's forecast (indoor alternatives surfaced on bad-weather days).
- [ ] Must-visit places are honored and slotted into the most geographically sensible day.
- [ ] Each item carries a one-line rationale (weather/geography/interest).

**P0.4 — Restaurant recommendations**
- [ ] Filtered for: open on the relevant date, dietary fit, budget band, proximity to that day's activities.
- [ ] At least one recommendation per meal slot the plan includes.
- [ ] Honest fallback when no match: show closest viable options, labeled as such.

**P0.5 — Weather-aware packing list**
- [ ] Generated from the destination's forecast across travel dates (e.g., rain → umbrella; cold → layers).

**P0.6 — Interactive map**
- [ ] All itinerary stops plotted, visually distinguishable by day.
- [ ] Demonstrates the geographic clustering at a glance (the hero visual).

**P0.7 — Backup in every slot**
- [ ] Every activity and meal slot includes at least one alternative.

### Nice-to-Have (P1) — fast follows
- **P1.1** One-tap slot swap that replaces the primary with its backup (serves Dan & Priya directly).
- **P1.2** Shareable static trip summary page (clean visual itinerary; the recap-video replacement).
- **P1.3** Transit/walking time estimates between clustered stops.
- **P1.4** Budget roll-up — estimated total spend across the plan.

### Future Considerations (P2) — design for, don't build
- **P2.1** Real-time on-trip re-planning. *Implication:* keep the plan as structured, mutable data, not a flat text blob.
- **P2.2** Families/business/group modes. *Implication:* model "traveler profile" as extensible, not hardcoded to one solo/couple shape.
- **P2.3** Post-trip recap video. *Implication:* keep itinerary + photos linkable to a trip object.
- **P2.4** Bookings/reservations. *Implication:* preserve each place's external ID so a booking link can attach later.

## 6. Success Metrics

### Leading indicators (build/demo quality)
- **Plan completeness:** 100% of generated plans include all six P0 outputs (itinerary, restaurants, packing list, map, backups, rationales). *Method:* checklist over 10 test destinations.
- **Grounding integrity:** 0 fabricated places/hours across the 10 test destinations. *Method:* spot-check every surfaced restaurant against its source. **This is the make-or-break metric.**
- **Geographic sanity:** ≥90% of days pass a "no silly backtracking" eyeball check on the map.
- **Sparse-input robustness:** a plan generated from *destination + dates only* is still complete and sensible.

### Lagging indicators (portfolio outcome)
- **Demo legibility:** a reviewer unfamiliar with the project can articulate "why this beats ChatGPT" within 30 seconds of seeing the map/reasoning view. *Method:* test on 3 people.
- **Reusability:** the data + planning layer works on a *new, untested* destination without code changes.

### Targets
- **Success threshold:** all P0 outputs present, grounding integrity = 100%, geographic sanity ≥90% on 3 demo cities (e.g., Lisbon, Tokyo, Barcelona).
- **Stretch:** robust on 10 cities including thinner-coverage destinations, with graceful "thin data" messaging.

## 7. Open Questions

**Blocking (resolve before building):**
- **[Data]** Which places API — Google Places (rich, paid, key required) vs. OpenStreetMap/Overpass (free, variable coverage/hours)? *Determines the entire grounding layer.* → Resolve via the data-layer spike.
- **[Data]** Do free sources reliably return *opening hours* and *cuisine/dietary tags*? If not, how do we filter for "open on date" and dietary fit? → Same spike.

**Non-blocking (resolve during build):**
- **[Eng]** Geographic clustering algorithm — simple proximity grouping vs. anything smarter? Start simple; revisit only if the map looks bad.
- **[Eng/Design]** Tech stack and platform — undecided (deferred by stakeholder).
- **[Design]** What does the map + reasoning hero view look like? Needs a rough wireframe before UI work.
- **[Data]** How is "budget band" defined and mapped to place price levels?

## 8. Timeline Considerations

No hard external deadline (portfolio project). Suggested phasing:

- **Phase 0 — Data-layer spike (do first).** Validate places + weather on one city: can we get location, open-hours, and dietary/cuisine data cleanly? *Go/no-go gate for the whole grounding premise.*
- **Phase 1 — Core engine.** Intake → grounded data → clustered, weather-aware itinerary with rationales + backups (P0.1–P0.3, P0.7).
- **Phase 2 — Supporting outputs.** Restaurants, packing list (P0.4–P0.5).
- **Phase 3 — The hero.** Interactive map (P0.6) — the demo centerpiece.
- **Phase 4 — Polish / fast follows.** Slot swap, shareable summary (P1).

**Critical dependency:** everything downstream depends on Phase 0. If the data layer can't deliver grounded open-hours/dietary data, the grounding goal (and the wedge) must be rethought before any further build.
